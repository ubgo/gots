# Configuration Approaches (Brainstorm)

All possible ways to configure gots — from YAML to code-as-config to comment DSLs. This is a design exploration document, not a user guide.

For the current config reference, see [README.md](../README.md#configuration-gotsyaml).

---

## YAML Config vs Code-as-Config: Key Trade-off

The most important distinction between these approaches is **file reach**.

> **YAML config can reference any file anywhere on disk; code-as-config can only configure types within its own package.**

### YAML config can point anywhere

```yaml
sources:
  # Your own packages
  - file: "pkg/constants/constants.go"
    output: "./frontend/src/types/constants.ts"

  # Another repo entirely
  - file: "/home/user/other-project/pkg/types/shared.go"
    output: "./frontend/src/types/shared.ts"

  # Vendor directory — types from dependencies
  - file: "vendor/github.com/stripe/stripe-go/v76/charge.go"
    output: "./frontend/src/types/stripe.ts"

  # Monorepo sibling service
  - file: "../billing-service/pkg/models/invoice.go"
    output: "./frontend/src/types/billing.ts"

  # Generated protobuf types
  - file: "gen/proto/user/v1/user.pb.go"
    output: "./frontend/src/types/proto.ts"
```

YAML config takes **absolute or relative file paths**. It can reach into:
- Any directory on the filesystem
- Vendor directories (convert third-party types)
- Other repositories in a monorepo
- Generated code directories (protobuf, sqlc, ent)
- Files outside your Go module entirely

This is a fundamental capability that code-as-config cannot match.

### Code-as-config is package-scoped

```go
//go:build gots

package constants  // ← this file must live in the same package

import "github.com/khanakia/gots/schema"

var _ = schema.Configure(
    schema.ForType(MessageRole(""),  // can only reference types in this package
        schema.Style(schema.Union),
    ),
)
```

Code-as-config files live **inside the package they configure**. They can only reference types from that package (or imported packages, but can't configure imported types). You cannot:
- Configure a type from a vendor dependency (you can't add files to vendor/)
- Configure types from another repo (you can't add gots.config.go to their source)
- Have a single config file that configures types across multiple packages

### Side-by-side comparison

| Capability | YAML Config | Code-as-Config |
|---|---|---|
| **Point to any file on disk** | Yes | No (package-scoped) |
| **Vendor/dependency types** | Yes (path to vendor/) | No (can't add files to vendor/) |
| **Monorepo cross-service** | Yes (relative paths) | No (each service is isolated) |
| **Generated code (proto, sqlc)** | Yes (path to gen/) | Possible but fragile |
| **Single config for everything** | Yes (one gots.yaml) | No (one file per package) |
| **Intellisense on type names** | No (strings) | Yes (Go LSP) |
| **Refactor-safe** | No (rename breaks config) | Yes (IDE renames propagate) |
| **Type-checked config** | No (runtime errors) | Yes (compile errors) |

### Recommendation

**YAML is the primary config format** — it handles every use case. Code-as-config is a future opt-in addition for users who want refactor safety on their own packages and don't mind the per-package config file. The two can coexist: YAML for global settings and cross-project sources, code-as-config for per-package type overrides.

## The Decision Problem

For any Go type, the tool needs to know:

- **Include or skip?** Should this type be converted at all?
- **What style?** Union, enum, const-object, interface, type alias?
- **What name?** Keep the Go name, rename it, strip prefix?
- **Field-level overrides?** Skip a field, change its TS type, make it optional?
- **Output target?** Which `.ts` file does it go into?
- **Global settings?** Type maps, pointer handling, struct tag source?

## Approach 1: YAML Config File

A standalone `gots.yaml` at the project root.

```yaml
default_style: union
emit_values_array: false
struct_tag: json
pointer_handling: optional     # optional | nullable | both
empty_interface: unknown       # unknown | any
header: "// Code generated by gots. DO NOT EDIT."

type_map:
  time.Time: string
  uuid.UUID: string
  decimal.Decimal: string
  json.RawMessage: unknown
  pq.StringArray: string[]
  net.IP: string
  sql.NullString: string | null

sources:
  - file: "pkg/constants/constants.go"
    output: "./frontend/src/types/constants.ts"
    style: const-object
    include:
      - "MessageRole"
      - "Feedback*"
      - "ItemGroupSource*"
    exclude:
      - "ItemGroupSourceStatus"   # deprecated

  - file: "pkg/models/*.go"
    output: "./frontend/src/types/models.ts"
    struct_style: interface       # interface | type
    embed_strategy: extends       # flatten | extends | intersection

overrides:
  MessageRole:
    style: union
    values_array: true
  LockType:
    style: enum
  FeedbackCategory:
    style: enum
    name: FeedbackType            # rename in TS output
  User:
    fields:
      CreatedAt:
        type: Date
      password:
        skip: true
```

**Pros:**
- Single file, full picture of all generation
- Easy to review in PRs
- Supports glob patterns for files and type names
- All settings in one place

**Cons:**
- No connection to Go source — type names are strings, can typo
- No autocomplete on type names
- Renaming a Go type doesn't update the config
- Separate file to maintain

## Approach 2: YAML Config + JSON Schema (Intellisense for Free)

Same YAML config, but publish a JSON Schema so editors provide autocompletion.

```yaml
# yaml-language-server: $schema=https://raw.githubusercontent.com/khanakia/gots/main/schema.json

default_style: union          # editor autocompletes: union | enum | const-object
pointer_handling: optional    # editor autocompletes: optional | nullable | both
struct_tag: json              # editor autocompletes: json | yaml | db | toml

sources:
  - file: "pkg/constants/constants.go"
    output: "./frontend/src/types/constants.ts"
    style: const-object       # autocomplete kicks in
```

**How it works:**
- JSON Schema defines every key, its allowed values, descriptions, and defaults
- VS Code (with Red Hat YAML extension), JetBrains, and others read the schema
- User gets autocomplete on keys (`default_style`, `pointer_handling`, etc.)
- User gets autocomplete on values (`union`, `enum`, `const-object`)
- User gets validation (red squiggles on invalid values)
- User gets hover docs (description from the schema)

**What you build:**
- A `schema.json` file shipped with the project
- Reference it from the YAML file or register it in editor settings

**Setup: VS Code**

1. Install the **"YAML" by Red Hat** extension (`redhat.vscode-yaml`) from the VS Code marketplace.

2. Add the schema comment as the first line of your `gots.yaml`:

```yaml
# yaml-language-server: $schema=https://raw.githubusercontent.com/khanakia/gots/main/schema.json
```

Or use a local relative path if the remote URL is slow:

```yaml
# yaml-language-server: $schema=./schema.json
```

3. Reload VS Code (`Cmd+Shift+P` → `Developer: Reload Window`).

4. Verify the bottom-right status bar shows `YAML` (not `Plain Text`). If not, click it and select `YAML`.

**Triggering autocomplete:**

- On an empty line, press `Ctrl+Space` to see all available properties.
- On macOS, `Cmd+Space` is captured by Spotlight by default. Either:
  - Disable Spotlight shortcut: System Settings → Keyboard → Keyboard Shortcuts → Spotlight → uncheck "Show Spotlight search"
  - Or use `Cmd+Shift+P` → type `Trigger Suggest` → press Enter
  - Or rebind: open Keyboard Shortcuts (`Cmd+K Cmd+S`), search `editor.action.triggerSuggest`, and assign a different key
- Start typing any property name (e.g., `d` for `default_style`) and suggestions appear automatically.

**Alternative: configure schema globally in VS Code settings**

If you don't want the schema comment in every file, add this to your VS Code `settings.json` (`Cmd+Shift+P` → `Preferences: Open User Settings (JSON)`):

```json
{
  "yaml.schemas": {
    "https://raw.githubusercontent.com/khanakia/gots/main/schema.json": "**/gots.yaml"
  }
}
```

This auto-applies the schema to any file named `gots.yaml` without needing the comment.

**Pros:**
- No custom editor extension to build or maintain
- Works in VS Code, JetBrains, Vim (with YAML LSP), Neovim
- Users get autocomplete and validation on day one
- Schema itself serves as documentation

**Cons:**
- Autocomplete only on config keys/values, not on Go type names
- Can still typo type names in `overrides` and `include`
- Schema needs to stay in sync with the tool's config parser

## Approach 3: TOML Config File

Same concept as YAML, different format. Some people prefer TOML for CLI tools (Cargo, Hugo, etc.).

```toml
default_style = "union"
emit_values_array = false
struct_tag = "json"
pointer_handling = "optional"
header = "// Code generated by gots. DO NOT EDIT."

[type_map]
"time.Time" = "string"
"uuid.UUID" = "string"
"decimal.Decimal" = "string"
"json.RawMessage" = "unknown"

[[sources]]
file = "pkg/constants/constants.go"
output = "./frontend/src/types/constants.ts"
style = "const-object"
include = ["MessageRole", "Feedback*"]
exclude = ["ItemGroupSourceStatus"]

[overrides.MessageRole]
style = "union"
values_array = true

[overrides.LockType]
style = "enum"
```

**Pros:**
- Well-supported in Go ecosystem (BurntSushi/toml, pelletier/go-toml)
- TOML has a spec, less ambiguity than YAML
- JSON Schema equivalent exists (taplo) for editor support

**Cons:**
- Nested structures are more verbose than YAML
- Less familiar to frontend developers
- Same string-based type name problem

## Approach 4: Go Code-as-Config (Full Intellisense)

Instead of a config file, use a Go file that imports a `gots/schema` package. The Go LSP provides full intellisense — no custom extension needed.

```go
// gots.config.go
//go:build gots

package constants

import "github.com/khanakia/gots/schema"

var _ = schema.Configure(
    schema.Output("./frontend/src/types/constants.ts"),
    schema.DefaultStyle(schema.Union),
    schema.EmitValuesArray(false),

    schema.Type("MessageRole",
        schema.Style(schema.Union),
        schema.ValuesArray(true),
    ),

    schema.Type("FeedbackCategory",
        schema.Style(schema.Enum),
    ),

    schema.Type("LockType",
        schema.Style(schema.ConstObject),
    ),

    schema.Skip("InternalThing"),
)
```

**With type references (refactor-safe):**

```go
//go:build gots

package constants

import "github.com/khanakia/gots/schema"

var _ = schema.Configure(
    // Referencing actual Go types — IDE rename propagates here
    schema.ForType(MessageRole(""),
        schema.Style(schema.Union),
        schema.ValuesArray(true),
    ),

    schema.ForType(FeedbackCategory(""),
        schema.Style(schema.Enum),
    ),

    schema.ForType(User{},
        schema.StructTag("json"),
        schema.Pointers(schema.Nullable),
        schema.Field("CreatedAt", schema.TSType("Date")),
        schema.Field("password", schema.SkipField()),
    ),

    schema.SkipType(InternalThing("")),
)
```

**What the user gets from Go LSP for free:**
- Autocomplete on `schema.Style(schema.` → shows `Union`, `Enum`, `ConstObject`
- Autocomplete on `schema.` → shows all available functions
- Hover docs on every function (from Go doc comments on the schema package)
- Compile-time errors if you reference a type that doesn't exist
- IDE rename: rename `MessageRole` → config updates automatically
- Go vet / build catches invalid config at dev time

**How `//go:build gots` works:**
- Normal `go build` ignores this file (build tag not set)
- `gots` tool parses it with the build tag enabled
- Zero impact on your binary size or compilation

**Pros:**
- Full intellisense in every Go editor on day one
- Type-safe — impossible to reference a nonexistent type
- Refactor-safe — IDE renames propagate
- No custom editor extension to build
- It's just Go — no new syntax to learn
- Colocated with the source code it configures

**Cons:**
- Config is spread across packages (each package has its own `gots.config.go`)
- No single-file view of all generation settings
- Need to publish and maintain the `schema` Go package
- Users must `go get` the schema package (even though it's build-tag excluded)

## Approach 5: Inline Comment DSL

Comment annotations directly on Go types.

```go
//gots:style=union
//gots:values_array
type MessageRole string

//gots:skip
type InternalThing string

//gots:style=enum
//gots:name=FeedbackType
type FeedbackCategory string

type User struct {
    ID        int64     `json:"id"`

    //gots:type=Date
    CreatedAt time.Time `json:"created_at"`

    //gots:optional
    Name string `json:"name"`

    //gots:skip
    password string
}
```

**Available directives:**

| Directive | Applies to | Description |
|---|---|---|
| `//gots:style=union` | type | Output style: `union`, `enum`, `const-object` |
| `//gots:skip` | type, field | Exclude from generation |
| `//gots:name=Foo` | type | Rename in TS output |
| `//gots:values_array` | type | Also emit values array |
| `//gots:type=Date` | field | Override TS type for this field |
| `//gots:optional` | field | Force field to be optional |
| `//gots:nullable` | field | Force field to be nullable |
| `//gots:inline` | field (embedded struct) | Flatten instead of extends |
| `//gots:output=path.ts` | type | Override output file |

**Pros:**
- Config is colocated right next to the code it affects
- Easy to read — you see the Go type and its TS config together
- No separate file to maintain
- Familiar pattern (Go uses `//go:generate`, `//go:embed`, etc.)

**Cons:**
- No autocomplete or validation without a custom editor extension
- Clutters Go source with TS concerns
- Hard to get a full picture of all generation settings
- Can't express global settings (type maps, defaults)

## Approach 6: Inline Comment DSL + VS Code Extension (Intellisense)

Same comment DSL as Approach 5, but with a purpose-built editor extension.

```go
//gots:style=union     ← typing "//gots:" triggers autocomplete
//gots:values_array    ← extension knows all valid directives
type MessageRole string
```

**What the extension provides:**
- Typing `//gots:` shows all available directives
- Typing `//gots:style=` shows `union | enum | const-object`
- Red squiggles on invalid directives or values
- Hover shows docs for each directive
- Quick fixes: "Did you mean `//gots:style=union`?"
- Code lens: shows preview of what TS will be generated

**What you need to build:**
- VS Code extension (TypeScript-based)
- Parse Go files, find `//gots:` comments
- Provide completion items, diagnostics, hover info
- Optionally: JetBrains plugin (Kotlin-based, separate codebase)
- Optionally: LSP server (works with any editor)

**Pros:**
- Best colocated DX — autocomplete right where you write config
- Code lens preview would be compelling

**Cons:**
- Must build and maintain an editor extension
- Two codebases if you want JetBrains support
- Or build an LSP server (more work upfront, but editor-agnostic)
- Users must install the extension to get the DX benefit

## Approach 7: Struct Tags for Field Config

Use Go struct tags for field-level configuration (works alongside any other approach for type-level config).

```go
type User struct {
    ID        int64     `json:"id" ts:"type:number"`
    Name      string    `json:"name"`
    CreatedAt time.Time `json:"created_at" ts:"type:Date"`
    Email     *string   `json:"email" ts:"optional,nullable"`
    Password  string    `json:"password" ts:"-"`
    Meta      any       `json:"meta" ts:"type:Record<string,unknown>"`
    Score     float64   `json:"score" ts:"branded"`
}
```

**Tag syntax:**

| Tag value | Meaning |
|---|---|
| `ts:"-"` | Skip this field |
| `ts:"type:Date"` | Override TS type |
| `ts:"optional"` | Force optional (`?`) |
| `ts:"nullable"` | Force nullable (`\| null`) |
| `ts:"optional,nullable"` | Both (`?: T \| null`) |
| `ts:"branded"` | Use branded type |
| `ts:"name:createdAt"` | Override TS field name |
| `ts:"readonly"` | Add `readonly` modifier |

**Pros:**
- Natural Go pattern — struct tags are the standard way to annotate fields
- Colocated with the field definition
- Some editor support for struct tags already exists
- Familiar to anyone who's used `json`, `yaml`, `db` tags

**Cons:**
- Only works for struct fields, not types or const blocks
- No autocomplete on tag values without custom tooling
- Adds noise to already-long struct tags
- `go vet` doesn't know about `ts` tags (but custom vet checks can be added)

## Approach 8: Go Generate + Marker Interfaces

Use Go's `//go:generate` with marker interfaces or types to indicate what should be converted.

```go
//go:generate gots generate --output=./frontend/src/types

// Marker: any type that embeds gots.Export gets converted
type MessageRole string // implements gots.TSType via method

func (MessageRole) GotsConfig() gots.TypeConfig {
    return gots.TypeConfig{
        Style: gots.Union,
        ValuesArray: true,
    }
}

type User struct {
    // ...
}

func (User) GotsConfig() gots.TypeConfig {
    return gots.TypeConfig{
        Style: gots.Interface,
        Pointers: gots.Nullable,
    }
}
```

**Pros:**
- Full Go intellisense on config methods
- `//go:generate` is the standard Go pattern for code generation
- Config is actual Go code, type-checked

**Cons:**
- Pollutes your types with methods that only exist for code generation
- Methods show up in docs, autocomplete on the type itself
- Build-tag trick doesn't work here (methods must be on the actual type)
- Verbose for types that just need defaults

## Approach 9: Separate Config Package (Registry Pattern)

A dedicated Go package that registers types for conversion. Similar to how `database/sql` drivers work.

```go
// internal/gots/registry.go
package gotsconfig

import (
    "github.com/khanakia/gots/schema"
    "myapp/pkg/constants"
    "myapp/pkg/models"
)

func init() {
    schema.Register(constants.MessageRole(""),
        schema.Style(schema.Union),
        schema.ValuesArray(true),
    )

    schema.Register(constants.FeedbackCategory(""),
        schema.Style(schema.Enum),
    )

    schema.Register(models.User{},
        schema.Pointers(schema.Nullable),
        schema.Field("CreatedAt", schema.TSType("Date")),
    )

    schema.SetDefaults(
        schema.DefaultStyle(schema.Union),
        schema.TypeMap(map[string]string{
            "time.Time": "string",
            "uuid.UUID": "string",
        }),
    )
}
```

**Pros:**
- Single file, full picture of all registrations
- Full Go intellisense — real type references
- Refactor-safe
- Clean separation — types don't know about gots

**Cons:**
- Separate package that imports all your other packages (import graph concerns)
- Must be kept in sync manually when new types are added
- Less discoverable — config is far from the types it describes

## Approach 10: Hybrid Comment DSL with Structured Blocks

A richer comment syntax that supports blocks, not just single-line directives.

```go
/*gots
output: ./frontend/src/types/constants.ts
style: union
*/

type MessageRole string

const (
    MessageRoleUser      MessageRole = "user"
    MessageRoleAssistant MessageRole = "assistant"
    MessageRoleSystem    MessageRole = "system"
)

/*gots
style: enum
name: FeedbackType
values_array: true
*/
type FeedbackCategory string

/*gots
struct_tag: json
pointers: nullable
fields:
  CreatedAt: { type: Date }
  password: { skip: true }
*/
type User struct {
    // ...
}
```

**Pros:**
- Full YAML-like config but colocated with the type
- Can express complex settings (field overrides, nested config)
- No separate file
- `gots` tool parses these block comments via AST

**Cons:**
- No intellisense without custom extension
- Go formatters might reformat block comments
- Unfamiliar pattern — neither standard Go nor standard YAML
- Verbose for simple cases

## Approach 11: `.gots` Sidecar Files

A `.gots` file next to each Go file, like `.d.ts` files in TypeScript.

```
pkg/constants/
├── constants.go
└── constants.gots        ← sidecar config
```

`constants.gots`:

```yaml
output: ./frontend/src/types/constants.ts
style: const-object

types:
  MessageRole:
    style: union
    values_array: true
  FeedbackCategory:
    style: enum
  InternalThing:
    skip: true

fields:
  User:
    CreatedAt: { type: Date }
    password: { skip: true }
```

**Pros:**
- Config lives next to the file it describes
- Not inside Go source — no clutter
- Can use JSON Schema for intellisense (it's just YAML)
- Easy to see which Go files have gots config

**Cons:**
- Many small files to maintain
- Easy to forget to update when Go file changes
- String-based type names — no refactor safety
- Less visible than inline config

## Precedence / Cascade

If multiple approaches are supported, how do they combine? Most specific wins.

```
Priority (highest to lowest):

1. Struct tags          ts:"-"                    Field-level, highest specificity
2. Inline comments      //gots:style=union        Type-level, colocated
3. Code-as-config       gots.config.go            Package-level, type-safe
4. Sidecar file         constants.gots            File-level
5. YAML/TOML config     gots.yaml overrides       Per-type overrides
6. YAML/TOML config     gots.yaml sources         Per-file defaults
7. YAML/TOML config     gots.yaml defaults        Global defaults
8. Auto detection                                  Built-in heuristics
```

## Recommended Combinations

### Minimal (ship fast)

Just YAML + JSON Schema. Covers everything, intellisense on config values.

```
gots.yaml  +  schema.json
```

### Balanced (good DX, no custom tooling)

YAML for global settings + Go code-as-config for per-type settings.

```
gots.yaml               → output paths, type maps, global defaults
gots.config.go (per-pkg) → per-type style, field overrides (with full intellisense)
```

### Full (maximum DX)

YAML + Go code-as-config + struct tags + comment DSL with extension.

```
gots.yaml               → global settings, output paths
gots.config.go           → type-level config (intellisense from Go LSP)
ts:"..." struct tags     → field-level config (familiar pattern)
//gots: comments         → quick one-offs (intellisense from extension)
VS Code extension        → autocomplete on comments, preview panel
```

### Pragmatic (recommended starting point)

YAML + JSON Schema for everything. Add code-as-config later if users want refactor safety.

```
gots.yaml  +  schema.json    (v1.0)
gots.config.go                (v2.0, optional)
```
